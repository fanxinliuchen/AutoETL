# 云表接入设计方案（连接注册中心 + 云表抽取）

| 项 | 内容 |
|---|---|
| 状态 | 待评审（本文只做设计，未改代码） |
| 目标 | 把「数据库连接 / 金蝶鉴权 / 云表鉴权」统一为**连接**，新建任务时选连接，运行时自动取鉴权参数 |
| 分期 | 一期地基 → 二期云表 → 三期前端收敛，每期独立可验收 |
| 影响表 | `t_etl_datasource`、`t_etl_pipeline`、`t_etl_kingdee_credential`（只读兼容） |
| 影响模块 | 数据源、流水线执行器、WebAPI 抽取、目标表结构、前端数据源弹窗与 Tab2 |

---

## 1. 背景

当前系统有三类外部系统，但只有一类被当成"数据源"：

| 系统 | 现状存法 | 问题 |
|---|---|---|
| MySQL 数仓 | `t_etl_datasource`（JDBC 形状） | 只支持数据库 |
| 金蝶 K3Cloud | 流程内 `api_auth_config` + `t_etl_kingdee_credential` | N 条流程各存一份，改密码要逐条改 |
| 云表 | 无 | 未接入 |

集团物联平台的"数据分发"已把三者统一在注册中心里管理。本系统对齐这个形态，同时解决配置重复问题。

---

## 2. 设计原则

> **连接 = 怎么连 + 怎么鉴权；流程 = 取什么 + 落到哪。**

据此划分参数归属：

| 参数 | 归属 | 理由 |
|---|---|---|
| host / port / database / 账号 / 密码 / 连接池 | 连接 | 换环境只改一处 |
| 金蝶 loginUrl / 账套 / 账号 / 密码 / lcid | 连接 | 同一账套下所有单据共用；单据查询地址属于流程 |
| 云表 baseUrl / appName / appKey / 账号 / 密码 / 超时 | 连接 | 同一应用空间共用 |
| 金蝶 FormId / FieldKeys / FilterString | 流程 | 每个任务不同 |
| 云表 模板名称 / 数据接口名称 / paramList / filter | 流程 | 每个任务不同 |
| MySQL 抽取 SQL | 流程 | 每个任务不同 |
| 目标表名 / 写入模式 / 转换 SQL | 流程 | 每个任务不同 |

---

## 3. 目标架构

```
          MySQL 连接            金蝶连接             云表连接
              │                    │                    │
              └────────────┬───────┴────────────────────┘
                           ▼
                连接注册中心（t_etl_datasource）
                conn_type + config_cipher + 测试连接
                           │
                    ConnectionFactory（按类型分派）
                           │
        ┌──────────────────┼───────────────────┐
        ▼                  ▼                   ▼
   HikariDataSource   KingdeeAuthProvider   YunbiaoAuthProvider
   （现有，不动）      （cookie 缓存）        （token 缓存 + 现算签名）
        │                  │                   │
        └──────────────────┴───────────────────┘
                           ▼
             抽取 → 暂存表 → 转换 SQL → 入库 → 调度/告警（全部复用）
```

## 4. 数据模型

### 4.1 连接表：原地升级 `t_etl_datasource`

**为什么不新建一张 `t_etl_connection`**：流程表的 `source_ds_id` / `target_ds_id` 已经指向这张表，原地升级后**这两列语义自然扩展为「连接ID」，不需要新增列、不需要双读**。新建表的代价是两张表并存 + 全量迁移 + 所有引用点改字段名。

**为什么不是"给云表加 6 个字段"**：那是加**类型专属列**，每接一种系统就要加一批，表会变成"什么都有一点、什么都不完整"。这里只加 **2 个通用列**（类型 + 加密 JSON），类型差异全部收进 JSON。

```sql
ALTER TABLE t_etl_datasource
  ADD COLUMN conn_type     VARCHAR(32) NOT NULL DEFAULT 'MYSQL'
      COMMENT '连接类型: MYSQL / KINGDEE_K3 / IYUNBIAO' AFTER ds_name,
  ADD COLUMN config_cipher TEXT NULL
      COMMENT '非 MySQL 类型的连接配置(JSON, AES 加密)' AFTER password_cipher;

-- 这三列当前是 NOT NULL，云表/金蝶行填不进去，必须放开
ALTER TABLE t_etl_datasource
  MODIFY COLUMN jdbc_url        VARCHAR(512) NULL COMMENT 'JDBC连接串(仅 MYSQL 必填)',
  MODIFY COLUMN username        VARCHAR(64)  NULL COMMENT '用户名(仅 MYSQL 必填)',
  MODIFY COLUMN password_cipher VARCHAR(512) NULL COMMENT '加密密码(仅 MYSQL 必填)';
```

各类连接的 `config_cipher` 解密后结构：

```jsonc
// MYSQL：沿用现有列，config 留空（存量数据零迁移）

// KINGDEE_K3（只存登录地址；取哪张单据由流程的接口地址决定）
{
  "loginUrl": "http://39.98.122.240/K3Cloud/.../ValidateUser.common.kdsvc",
  "acctID": "5e002a8e220b48",
  "userName": "bi",
  "password": "******",
  "lcid": 2052
}

// IYUNBIAO
{
  "baseUrl": "http://yunbiao.whstby.cn/10001",
  "appName": "992d3273-e2d4-41e1-97be-35aa134ceb57",
  "appKey": "131b916d-b2be-48bd-bbe1-baccdefacf47",
  "userName": "test3",
  "password": "******",
  "timeoutMs": 15000
}
```

> 加密沿用 `etl.security.cipher-key`（`ETL_CIPHER_KEY`）这把已有钥匙，不引入新密钥。列表接口只返回掩码，永不回显密码与 AppKey。

### 4.2 流程表：不新增列

| 现状 | 一期后 |
|---|---|
| `source_ds_id` → MySQL 数据源 | `source_ds_id` → 任意 `conn_type` 的连接 |
| `target_ds_id` → MySQL 数仓 | 不变（目标只允许 `conn_type=MYSQL`，下拉过滤） |
| `source_type` = MYSQL / WEB_API | 不变。云表复用 `WEB_API`，靠连接的 `conn_type` 区分 |

> 一期刻意**不新增 `source_conn_id`**：`source_ds_id` 已经指向同一张表，改名只会带来迁移成本。

### 4.3 存量数据

| 存量 | 处理 |
|---|---|
| `t_etl_datasource` 4 行 | `conn_type` 默认 `MYSQL`，无需迁移 |
| `t_etl_kingdee_credential` 1 行 | 保留只读。提供「一键迁移为连接」按钮，迁移后仍可用旧凭证兜底 |
| 4 条流程的 `api_auth_config` | **保留**，作为兜底（见 §5.3） |

## 5. 运行时

### 5.1 类型分派

```java
public interface ConnectionProvider {
    ConnTypeEnum type();
    /** MySQL 返回 DataSource；API 类返回 AuthSession */
    Object open(EtlDatasource conn);
}

public interface ApiAuthProvider {
    /** 每次请求现取（签名/时间戳每次不同） */
    Map<String, String> headers();
    /** 会话失效：清缓存，下次请求重登 */
    void invalidate();
}
```

- `MYSQL` → 走现有 `EtlDatasourceService.getDataSource()`，逻辑不变
- `KINGDEE_K3` → 把现有 `executePreAuth` 的 cookie 逻辑搬进 provider
- `IYUNBIAO` → 新增 provider（见 §6.1）

### 5.2 会话缓存与失效重登

```java
// key = connectionId，value 含 token/cookie + lastUsedAt
ConcurrentHashMap<Long, Session> sessions;
```

| 系统 | 缓存内容 | 失效判定 |
|---|---|---|
| 金蝶 | `kdservice-sessionid` cookie | 请求返回未登录/登录态错误 → `invalidate()` 后重试一次 |
| 云表 | `x-eversheet-session-token` | 空闲超 14 分钟预判重登；或业务错误码命中 → 重登一次 |

**重试只做一次**，避免死循环。并发场景用 `computeIfAbsent` + 单飞（同一连接同时只有一个登录在飞）。

> 现状是每条流程各自登录一次；统一后同一连接在多流程、多轮循环里只登一次，金蝶「多账套科目余额表」这种 5 轮循环能省 4 次登录。

### 5.3 鉴权参数取值顺序（双读）

```
1. source_ds_id 指向连接的 conn_type=KINGDEE_K3/IYUNBIAO  → 用连接里的配置（新）
2. 否则 api_auth_type=KINGDEE_K3 且 api_auth_config 有值 → 用流程里的（旧）
3. 否则 t_etl_kingdee_credential 默认凭证            → 兜底（旧）
```

老流程一行配置都不用改就能继续跑；新流程只认连接。三期把 2、3 两步标注废弃。

## 6. 云表接入详设

### 6.1 鉴权（已实测）

```java
// 签名：每次请求现算，不能缓存
// 注意：文档正文写「AppKey + 时间戳」，但文档自带示例是时间戳在前。
// 用示例验算（key=058457b7-…, ts=1389085779854 → F3DFAE8C1B952779ED068B9DB66BE258）
// 只有 ts+key 能对上；按正文拼接会被服务端判「签名验证不匹配」（已踩）
sign = MD5(timestamp + appKey).toUpperCase()

headers:
  Accept: application/json
  Content-Type: application/x-www-form-urlencoded       // 登入
  X-Eversheet-Application-Name: {AppName}
  X-Eversheet-Request-Sign: {sign},{timestamp}          // 时间戳 6 分钟内有效
  X-Eversheet-Session-Token: {token}                    // 登入请求留空
```

**登入接口**（已实测）

```
POST {baseUrl}/openapi/1.0/login        // baseUrl 已含 enpId，如 http://yunbiao.whstby.cn/10001
formData: loginJson={"account":"test3","password":"<MD5-32-大写>"}
返回: {"logout":"/logout","token":"…","serverVersion":"3.3.35.39","redirect":"/10001/","user":"test3"}
失败直接 500，正文 Exception.detail 带原因
```

- token 空闲 15 分钟过期，每次请求续期；缓存判定按 14 分钟保守处理
- 连接测试（`/etl/datasource/test-connection`）实测通过：「云表 OpenAPI 连接成功，鉴权已通过」

### 6.2 地址拼装

```
{baseUrl}/{表单模板名称}
例：http://yunbiao.whstby.cn/10001/openapi/1.0/表结合数采明细_IOT
```

`baseUrl` 含 `enpId`（本地服务第一个应用默认 `10001`），存连接；模板名存流程。

> **实测修正**：真实路径是 `{baseUrl}/openapi/1.0/{模板名}`，**不带 `/query` 那一段**。
> 写成 `{模板}/{数据接口}/query` 会报 `找不到数据接口[xxx]`（错误码 310175）；
> 少了 `openapi/1.0` 前缀则被当成网页请求，重定向登录页并报「连接超时，或其他人登入」。
> 流程里「接口地址」填相对路径 `openapi/1.0/表名`，后端自动拼服务地址。

### 6.3 报文表示（关键设计）

云表查询接口的表单字段是 **`formJson`**，值是**分页对象本身**：

```
Content-Type: application/x-www-form-urlencoded
formJson={"pageInfo":{...},"filter":[],"paramList":[...]}
```

> **实测修正**：不要把分页对象再包一层 `queryParams` 再塞进 `formJson`
> （即 `formJson={"queryParams":{...}}`）——服务端会忽略 `pageSize`，退回默认 50 条/页，
> 分页配置看起来生效实则无效。

如果直接把字符串存进流程，现有分页引擎（按 JSON 路径改写字段）就完全用不上。**方案：配置里存 JSON 对象，发送前才序列化。**

流程里保存的报文：

```json
{
  "formJson": {
    "pageInfo": {
      "isUseRowIndex": true,
      "rowIndex": 0,
      "pageSize": 2000
    },
    "filter": [
      { "filterField": "修改时间", "Operator": "$gte", "Value": "${begindate}", "isAnd": true },
      { "filterField": "修改时间", "Operator": "$lt",  "Value": "${enddate}",   "isAnd": true }
    ],
    "paramList": [
      { "param": "仓库", "value": "${仓库编码}" }
    ]
  }
}
```

抽取器在 `sendOnce` 之前做三步，顺序不能调换：

```
① 变量替换（现有 RequestVarResolver，作用在 JSON 对象上）
② 分页改写（现有 PaginationConfig，作用在 JSON 对象上）
③ 报文顶层字段逐个变成 formData 字段，对象值压成压缩 JSON 提交
```

这样**变量、循环、分页、附加列四套现成机制全部复用**。

「报文顶层字段即表单字段」这个规则是通用的：将来接云表的保存/删除接口（`formJson` 之外的字段名）
不用再改抽取器，按各自接口的表单字段名写报文即可。

### 6.4 分页

`pageInfo` 支持两种模式，二选一（`isUseRowIndex` 必须与所选模式一致，否则参数被忽略）：

| 模式 | 配置 | 说明 |
|---|---|---|
| **行号（推荐）** | `offsetPath=formJson.pageInfo.rowIndex`，`start=0`，`step=pageSize`，`limitPath=formJson.pageInfo.pageSize` | 与现有"偏移量"引擎 100% 契合 |
| 页码 | `offsetPath=formJson.pageInfo.pageIndex`，`start=0`，`step=1`，`limitPath=...pageSize` | **pageIndex 从 0 开始**，所以 start 必须是 0 |

推荐行号模式：不依赖 `pageCount/total` 是否准确，翻页到 `本页条数 < pageSize` 自动结束（现有 `endWhenLessThan` 已支持）。

> 注意：`pageIndex` 是 **0 起**，与常见分页习惯相反。UI 文案要写明，否则必然填成 1。

实测（`表结合数采明细_IOT`，36 行、每页 10 条）：4 次请求，偏移 0/10/20/30，累计 36 条，
最后一页 6 条触发结束——行号模式与服务端 `rowIndex` 语义完全一致。

### 6.5 过滤与查询参数

`filter[]` 的算子：

| 云表 Operator | 含义 | 现有结构化条件对应 |
|---|---|---|
| `$e` / `$ne` | 等于 / 不等于 | `=` / `<>` |
| `$gt` / `$gte` / `$lt` / `$lte` | 大于 / 大于等于 / 小于 / 小于等于 | 同名 |
| `10` / `11` | Like / NotLike | `LIKE` / `NOT LIKE` |
| `12` / `15` | In / NotIn | `IN` / `NOT IN` |
| `13` / `14` | IsNULL / IsNotNull | `IS NULL` / `IS NOT NULL` |

`paramList[]` 是数据接口的自定义查询参数（`param` + `value`），值支持 `${变量}`。

> **一期不改造「过滤条件」面板**：那个面板产出的是金蝶 `FilterString` 字符串，与云表的数组结构不同源。云表的 `filter`/`paramList` 直接写在报文 JSON 里，配合变量定义做时间窗口即可。面板适配放三期之后。

### 6.6 实跑样例：表结合数采明细_IOT

这是第一个跑通的云表流程，可作为后续接口的模板。

| 项 | 值 |
|---|---|
| 源连接 | `云表直连（dev）`（`IYUNBIAO`） |
| 接口地址 | `openapi/1.0/表结合数采明细_IOT`（相对路径，后端拼服务地址） |
| 结果提取 JsonPath | `$.results` |
| 分页 | 行号模式，`formJson.pageInfo.rowIndex` / `formJson.pageInfo.pageSize`，起始 0，页长 200 |
| 目标表 | `ods.ods_yunbiao_collect_detail_iot`（24 列，主键 `采集单编码`） |
| 写入 | `UPSERT`（主键更新） |
| 实测 | 36 行 / 1.3 秒 / 三次运行后总数仍 36（幂等） |

报文：

```json
{
  "formJson": {
    "pageInfo": { "isUseRowIndex": true, "pageCount": 0, "pageIndex": 0, "pageSize": 200, "rowIndex": 0, "total": 0 },
    "filter": [],
    "paramList": []
  }
}
```

**字段类型（按实测值定，不是猜的）**：

| 云表数据项 | 实测值 | 列类型 |
|---|---|---|
| `F03103` ~ `F03110` | 数值，带小数（`1380.04`） | `DECIMAL(18,4)` |
| `F03101` / `F03102` | 混合：`"0.0"` 或 `"2611161400"` / 时间串 | `VARCHAR(64)` |
| `公司名称` / `公司编码` / `采集单编码` / `状态` / `updatedBy` / `createdBy` 等 | 字符串 | `VARCHAR(n)` |
| `createdAt` / `updatedAt` | 干净的时间串 | `DATETIME` |
| `采集日期` | 干净的日期串 | `DATE` |
| `objectId` | 整数 | `BIGINT` |
| `objectVersion` | 整数 | `INT` |
| `objectLocked` | `null` / `false` | `VARCHAR(64)`（布尔落成 `"0"`） |

两条经验：

1. **空值不是空**：云表对「未填」的数值型数据项返回字符串 `"0.0"`，不是 `null` 也不是 `""`。
   这类列如果定成 `DATETIME` / `INT`，写入直接被严格模式拒掉。所以**混合类型的列一律用 `VARCHAR`**。
2. **先看数据再定类型**：同一个数据项在不同行里类型可能不同（日期列里混着 `"0.0"`），
   靠字段名猜类型必错。落库前先拉一页样本，逐列统计值类型分布，再定列类型。

### 6.6 结果解析与中文列名

结果解析沿用 `apiDataPath`：云表返回对象数组时走 `projectRecord` 按字段清单裁剪；返回二维数组时按字段清单下标对齐（现有逻辑已覆盖两种）。

**中文列名必须支持**——数仓里已有中文列名，云表数据项也基本是中文。当前有三处硬拦截：

| 位置 | 现状 | 改为 |
|---|---|---|
| `ColumnNaming.toColumn` | 非 ASCII 全部换成 `_` | 保留中文，只替换反引号 / 点 / 空格 / 控制字符 |
| `TargetTableSchemaService.IDENT` | `^[A-Za-z_][A-Za-z0-9_]{0,63}$` | 允许中文，仍禁反引号、分号、空白 |
| `RequestVarResolver.COLUMN_PATTERN` | 同上 ASCII-only | 同上 |

放开是安全的：建表、INSERT、SELECT 现有代码**已经用反引号包裹列名**；MySQL 8 + utf8mb4 原生支持中文列名（上限 64 字符，按字符计）。

字段清单增加一列 **「列名」**：

| 数据项名（发给云表） | 列名（落库） | 类型 |
|---|---|---|
| 物料名称 | 物料名称 | VARCHAR(255) |
| 规格型号 | spec_model | VARCHAR(255) |
| 数量 | 数量 | DECIMAL(18,4) |

留空时按「换算后的数据项名」兜底，保证存量流程行为不变。

### 6.7 错误与重试

- HTTP 非 200 → 抛 `ETL_EXECUTE_ERROR`，带状态码与响应片段
- 业务失败（返回体含错误码/提示）→ 需要一次实测确认字段位置，再在 `assertBusinessSuccess` 加云表分支
- token 失效 → 自动重登一次后重试当前页，日志标注「会话失效，已重登」
- 单页失败不吞：沿用现有「分页第 N 页失败（此前已成功 X 页 / Y 条）」的报错格式

## 7. 分期计划与验收

### 一期：地基（不动任何抽取逻辑）

改动：
1. `t_etl_datasource` 加 `conn_type` / `config_cipher`，放开三列 NOT NULL
2. `EtlDatasource` 实体 + 加解密（复用现有 AES）
3. `ConnectionFactory` + `KingdeeAuthProvider`（把现有 cookie 逻辑搬进来）
4. 数据源页面：类型下拉（MySQL / 金蝶 / 云表），按类型渲染表单；「测试连接」按类型分派
5. 目标数据源下拉只列 `conn_type=MYSQL`
6. 「一键迁移金蝶凭证」按钮

验收：
- [ ] 现有 4 条流程**不改任何配置**全部跑通（销售退货表、物料收发汇总表-周/月、多账套科目余额表）
- [ ] 数据源页可新建/编辑/测试三类连接，密码与 AppKey 不回显
- [ ] 停用某连接后，引用它的流程运行时报明确错误（不是 NPE）
- [ ] 金蝶连接测试能拿到 cookie；重复测试不产生会话泄漏

### 二期：云表抽取

改动：
